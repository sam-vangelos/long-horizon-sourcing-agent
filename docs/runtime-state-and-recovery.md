# Runtime State and Crash Recovery

Sourcing sessions run for hours against external browser sessions and rate-limited APIs. A run can terminate mid-page because of a browser disconnect, a network timeout, an operator interrupt (`SIGINT`), or a session cap. The runtime state layer in `shared/runtime_state/` is designed so that an interrupted campaign can resume from its last durable checkpoint without re-evaluating candidates it already judged or double-executing external saves.

## Canonical State vs. Projections

Each campaign state directory holds a SQLite database (`runtime_state.sqlite3`) managed by `RuntimeStateStore` in `shared/runtime_state/store.py`. Every connection opened by `RuntimeStateStore.connect()` sets `timeout=5.0`, executes `PRAGMA busy_timeout=5000`, `PRAGMA foreign_keys=ON`, and `PRAGMA journal_mode=WAL` (retried across transient `database is locked` errors via `_execute_with_lock_retry`), yields the connection to the caller, commits on context exit (`conn.commit()`), and closes the connection in `finally`.

Alongside `runtime_state.sqlite3`, adapters emit human-readable JSON and JSONL files (`progress.json`, `candidate_ledger.json`, `run_log.jsonl`) through `shared/runtime_state/projections.py` and the file helpers in `shared/storage.py`: `write_json` writes to a sibling temporary file created with `tempfile.mkstemp`, flushes and calls `os.fsync` on the temporary file descriptor, and atomically replaces the destination via `os.replace`, while `append_jsonl` opens the target file in append mode and writes a single newline-terminated JSON record. Those files are non-authoritative compatibility projections for operator inspection and downstream reporting. On `--resume`, every source adapter reconstructs its working control state from `runtime_state.sqlite3` rather than trusting projection files; in the LinkedIn adapter, `start_or_resume_linkedin_run` (`shared/runtime_state/linkedin_run_start.py`) calls `import_linkedin_legacy_state` (`shared/runtime_state/linkedin_legacy_import.py`) only when bootstrapping an older state directory whose canonical SQLite tables are not yet populated.

## Schema, Lifecycle Transitions, and Hash-Aware Deduplication

`RuntimeStateStore` maintains schema version `"12"` (`CURRENT_SCHEMA_VERSION = "12"` in `shared/runtime_state/store.py`). Tables are created inline in `RuntimeStateStore.initialize()`, evolved across versions by `_migrate()` (tracked in `schema_migrations`), and supplemented by `_install_external_schemas()`, which invokes `cloris.intake_sessions.install_schema`.

Candidate rows move through the eight states in `TARGET_CANDIDATE_LIFECYCLE`: `discovered`, `snippet_extracted`, `facial_started`, `facial_terminal`, `full_started`, `full_terminal`, `failed_retryable`, and `failed_terminal`. Transitions are checked by `_guard_transition` and `_guard_save_family_reentry` (called from `set_candidate_state` and `finish_attempt_success`). Under `ALLOWED_LIFECYCLE_TRANSITIONS`, `facial_terminal`, `full_terminal`, and `failed_terminal` allow transitions back to `snippet_extracted`, `facial_started`, or `full_started` so a previously rejected or failed candidate can be re-evaluated when the role brief changes. Once a candidate reaches `full_terminal` with a decision in `SAVE_FAMILY_DECISIONS` (`SAVE`, `INFERENTIAL_SAVE`, `TRANSFERABLE_SAVE`, `SIGNAL_SAVE`), `_guard_save_family_reentry` blocks any transition out of `full_terminal` unless the caller is retrying a failed or interrupted `linkedin_save` side effect.

Brief-hash-aware deduplication (`is_dedup_blocked` at `shared/runtime_state/store.py:1495-1529` and `list_terminal_identity_keys` at `shared/runtime_state/store.py:1428-1456`, using `_HASH_AWARE_SUPPRESSION_CLAUSE`) compares the active run's `runs.brief_content_hash` against `candidates.brief_content_hash` (a hash of the whole brief). Candidates whose `terminal_decision` is in `SAVE_FAMILY_DECISIONS` or whose `user_status` is non-null (recruiter-reviewed) stay suppressed across all subsequent runs regardless of brief edits; rejected or skipped terminal candidates are suppressed while `brief_content_hash` is unchanged and become eligible for re-evaluation when the brief hash changes.

## Advisory File Lock (`RuntimeStateLock`)

Before a session mutates state in a campaign directory, it acquires `runtime_state.lock` via `RuntimeStateLock` in `shared/runtime_state/lock.py`. `RuntimeStateLock.acquire()` opens the lock file and calls `fcntl.flock(handle.fileno(), fcntl.LOCK_EX | fcntl.LOCK_NB)`. If another live process holds the lock, `fcntl.flock` raises `BlockingIOError`, and `acquire()` closes its file handle and raises `RuntimeError(f"{self.resource_name} is already locked by another process")`. Because `fcntl.flock` is kernel-managed and tied to the open file description, the operating system releases the lock automatically if the holding process crashes or is killed with `SIGKILL` — no PID file parsing or lock-stealing logic is required in `lock.py`.

## External Side-Effect Ledger (`linkedin/side_effects.py`)

Saving a candidate to a LinkedIn Recruiter pipeline mutates external platform state through a browser click. If a session crashes while saving or attaching a note, a naive retry on `--resume` could double-click the control or drop a candidate who passed full evaluation.

`LinkedInSideEffectsService.handle_save_decision` (`linkedin/side_effects.py:52-357`) coordinates with the `side_effects` table through `LinkedInRuntimeStateBridge` (`shared/runtime_state/linkedin.py`) and `RuntimeStateStore.begin_candidate_side_effect` / `complete_candidate_side_effect` (`shared/runtime_state/store.py:2196-2489`), keyed by `UNIQUE(candidate_id, effect_type, idempotency_key)` with `effect_type="linkedin_save"` and `idempotency_key="save"` (and `effect_type="linkedin_note"`, `idempotency_key="note"` for follow-up notes):

1. Before clicking in the browser, `handle_save_decision` calls `runtime_bridge.begin_candidate_side_effect(..., effect_type="linkedin_save", idempotency_key="save")`.
2. If a row for `(candidate_id, 'linkedin_save', 'save')` already has `status = 'succeeded'`, `begin_candidate_side_effect` returns `"should_execute": False` without incrementing `attempt_count`, and `handle_save_decision` skips the browser save (`existing_succeeded`). Otherwise, `begin_candidate_side_effect` transitions the row to `status = 'pending'` in SQLite.
3. Before clicking `Save to pipeline`, `handle_save_decision` checks the live result card in the browser via `browser.is_already_saved_on_card(expected_identity)` and brackets the `browser.save_candidate(expected_identity)` call with `assert_expected_identity()` and `assert_project_context()` checks so a shifted card or wrong project tab aborts before actuation.
4. After DOM verification, `runtime_bridge.complete_candidate_side_effect` updates the `side_effects` row to `status = 'succeeded'` or `status = 'failed'`.

## Startup Reconciliation on `--resume`

When a LinkedIn session starts or resumes, `LinkedInRuntimeStateBridge.start_or_resume_run` (`shared/runtime_state/linkedin.py:81-113`) runs two crash-recovery passes before delegating to `start_or_resume_linkedin_run` (`shared/runtime_state/linkedin_run_start.py`):

1. `store.reconcile_open_attempts(source="linkedin", brief_id=self.brief_id)` (`shared/runtime_state/store.py:2139-2190`) selects every `candidate_attempts` row left in `status = 'started'`. For each orphaned attempt whose candidate is not already in `facial_terminal`, `full_terminal`, or `failed_terminal`, it transitions `candidates.current_lifecycle_state` to `failed_retryable`, and marks the attempt `status = 'reconciled'` with `failure_kind` set to `'orphaned_attempt'`.
2. `store.reconcile_pending_side_effects(source="linkedin", brief_id=self.brief_id)` (`shared/runtime_state/store.py:2516-2573`) transitions any `side_effects` row left in `status = 'pending'` to `status = 'interrupted'`. When the candidate is reprocessed on resume, `begin_candidate_side_effect` recognizes `existing_status == "interrupted"`, transitions it back to `pending` with `"replayed_from_interrupted": True` (without inflating `attempt_count`), and `handle_save_decision` checks `is_already_saved_on_card` before clicking so a save that succeeded just before the crash is recorded as `succeeded` without clicking a second time.
3. `start_or_resume_linkedin_run` (`shared/runtime_state/linkedin_run_start.py`) then creates the new `runs` row, restores saved work-unit checkpoints from `work_units`, and (only when migrating a legacy state directory) imports historical `progress.json` records via `import_linkedin_legacy_state`.
